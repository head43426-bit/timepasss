    Pass 4 — Follow the attack, step by step

    Three steps, in order: detect and label, connect the steps, explain and look ahead. Everything below is synthetic and runs in this browser only.

    Step 1 — Detect and label

    A detection engine reads each event and checks it against a rule catalogue (below). A flagged event gets a MITRE ATT&CK technique, a kill-chain stage, a confidence score, and a plain-words reason naming the matched word. Anything below the threshold is not labelled an attack — it is counted as benign and skipped. In the full version, the MITRE editor still works: editing a stage's technique changes what Step 1 shows for that stage.

    Defaults: direct window 60 minutes (a hop to another computer must be close in time and share a host or IP); credential window 2,880 minutes (48 hours — the same account reused days later, or the same computer across a long quiet gap, still links, but is labelled as a credential or host-continuity hop, never as a direct hop). Widening either window links more, but also risks joining two separate incidents — the link kind column shows you which kind each link is.

    Rule catalogue — what the engine looks for

    Step 2 — Connect the steps

    Flagged events are linked into one attack path. Link reasons are shown per edge: shared host, shared IP, same account reused, host continuity, or a credential chain (credentials obtained earlier in the path, then used on a new host). Events with no link to the path are left out — never invented into it. Memory design: events are processed in batches, only linked path nodes and per-key counts are kept, and the raw-event buffer is capped at 200 events. Benign events are counted, then dropped, so kept memory does not grow with the size of the log.

    Step 3 — Explain and look ahead

    Top row of the graph: computers. Bottom row: accounts. A line means that account acted on that computer in the linked path. Click or tab to a node (Enter/Space) to see its evidence. "What the attacker could reach next" is guessed only from the synthetic topology (same subnet, a service account used on server systems, a cloud API key created in the path) — if no topology covers a host, the panel says so instead of guessing.

    Large log test — find a concealed attack in thousands of events

    Honest label: this is a simulated scale test, not a real 50 GB file. Synthetic events are generated in batches (benign everyday activity plus 9 attack events spread over 3 days, hidden in the noise), then processed in batches of 500 with a progress bar, throughput, and the memory counters above. Only the linked path nodes and per-key aggregates are kept. The browser never holds a whole 50 GB file in memory, and this demo does not claim it does. The concealed attack links only because the same service account is reused across days (credential hops) and the attack stays on one workstation across a long gap (host continuity) — at a 60-minute direct window alone, it would not link, and the demo says so.

    Chunked file processor — full version only

    Demo / synthetic files only — do not upload real production logs. Pick a JSON-lines file (one JSON event per line) or a pipe-separated file (t|host|user|src|action|detail|stage|mitre|sev). The file is read in 64 KB slices, line by line; the whole file is never held as one string, nothing is stored or sent anywhere, and the same detect + link engine produces the same one-narrative output (Where it began / What the attacker did, in order / Which systems they can reach next).
