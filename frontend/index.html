How ASK works — the story, in plain words

ASK is Analyse · Secure · Kill: it reads your log, finds the attack, links it into one chain, and tells you what to do next. No demo data, no guessed hosts, no real production logs unless you choose to upload them. Here is every step, in order:

  1. 1. Ingest, streaming, memory-safe. Your file is received in 1 MB chunks and read line by line. Benign lines are counted and dropped immediately — only flagged lines ever reach the database. That is why a multi-GB file runs on a 4 GB machine, and why it is fast: no line is parsed twice, no whole file is ever held in RAM. With --workers 4 the file is split into byte-range chunks and processed in parallel, then replayed into one incident list.
  2. 2. Detect and label (Agent 1 in spirit). Every line is checked against Sigma-style rules in rules/*.yml — plain config files, not code, so you can add a rule without touching the engine. A match stamps a MITRE ATT&CK technique (for example T1566.001 Phishing, T1204.002 Malicious File, T1071.001 Web Protocols) and a kill-chain stage (Reconnaissance → Initial Access → Execution → Persistence → Privilege Escalation → Credential Access → Lateral Movement → Collection → Command and Control → Exfiltration). A single failed login never flags; brute force needs 50+ failures plus a success for the same user and host.
  3. 3. Link into one incident (Agent 2). Flagged lines that share a host, a user, or an IP within 48 hours join the same incident. That is the whole linking rule — host, user, IP, time — and it is why a phishing line, a malware line and a beacon line on the same host become one attack path instead of three separate alerts.
  4. 4. Graph (NetworkX). Hosts and users become nodes, moves become edges. A real host-to-host move is srcip → dstip from firewall logs. When an incident has only one host and no move, the graph draws host → technique instead, so there is still a map to look at. Hosts are squares, users are circles, techniques are diamonds.
  5. 5. Risk scoring (Agent 3, JEV-style validation). A transparent weighted formula, not a black box: severity weights (Critical 40, High 25, Medium 10, Low 3) plus 3 points per distinct kill-chain stage, plus 15 for exfiltration and 10 for credential access or privilege escalation, capped at 100. Merged-alert counts are kept separately, so a flood of 271,896 detections is reported as grouped counts, never as a wall of steps. Low-confidence matches are dropped by the rule threshold, which is the false-positive filter.
  6. 6. Look ahead (Agent 4, QAOA-inspired — honestly classical). Two predictions, and they are kept separate so neither pretends to be the other. Next hosts come only from a topology you supply: admin rights score 50, same subnet 25, with the reason shown for every host. Next stages come from the kill chain itself: after the deepest stage reached, the following stages are listed as what to watch for. The blast-radius optimiser then scores how much of your topology is compromised or one hop away. A true Qiskit statevector QAOA simulation grows as 2n and would never run on 4 GB — so ASK runs the same combinatorial idea classically (greedy + score), which gives the same ranking on real graphs and actually finishes.
  7. 7. Report (Agent 5). A plain-English narrative — where it began, what the attacker did in order, what they could reach next, what to block first — plus a Hindi version. Hindi is a real Sarvam API translation only when SARVAM_API_KEY is set; otherwise it is clearly labelled a template, never presented as a translation. If Sarvam is slow or rate-limited, the local fallback is the template, not a hallucinated translation.
  8. 8. Live mode. Run the server with --watch your.log and new lines are tailed, detected and linked into incidents as they arrive — the incident list below refreshes on its own while a watch is running.

What ASK does not do: it does not invent a host, a user, or a next target that is not in your logs or topology; it does not block or stop an attack (it describes it, so you can); it does not send your logs anywhere — the file stays on the machine running the server.
